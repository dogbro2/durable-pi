# 簡化技術英語

## 何時使用

出現以下任一情況時使用本技能：

- 寫或改 README、操作手冊、執行手冊、故障報告、釋出說明、API 指南。
- 文件面向非母語讀者，或需要機器翻譯後仍然可讀。
- 文本出現長句、同義詞輪換、被動語態堆疊或營銷腔。
- 使用者要求「簡化技術英語」「STE」「去 AI 味」「讓文件更好讀」。

不適用：文學創作、營銷文案、需要保留原始措辭的法律文本。

## 核心原則

1. **先分類，再改寫。** 每段先判斷是操作步驟還是解釋說明，兩類規則不同。
2. **一個概念只用一個詞。** 選定後全篇一致，不為了變化換同義詞。
3. **一句一個動作。** 操作步驟按執行順序寫，不把條件和動作混在一起。
4. **保留原文事實。** 程式碼、識別符號、命令列引數、檔案路徑、錯誤原文一律不改。
5. **不聲稱合規。** 本技能參考簡化技術英語規則，最終合規判斷由作者或標準稽核人負責。

## 第一步：分類段落

| 型別 | 用途 | 句式 | 句長上限 |
|---|---|---|---|
| 操作步驟 | 告訴讀者做什麼 | 祈使句 | 20 詞 |
| 解釋說明 | 說明是什麼、為什麼 | 一般現在時、過去時或將來時 | 25 詞 |

混合段落拆開：先寫一句說明，再列操作步驟。不要在一段裡既解釋原理又給指令。

## 第二步：統一術語

- 列出反覆出現的概念，每個概念選一個詞。
- 同義詞只保留一個，其餘在首次出現時標註「以下統一稱為 X」。
- 縮寫首次出現時寫全稱，之後統一用縮寫。
- 不為避免重複而換詞；技術寫作裡重複是優點。

## 第三步：改寫句子

- 操作步驟用祈使句，開頭就是動詞：安裝、開啟、執行、檢查。
- 條件放在指令前：如果配置為空，先填預設值，再啟動服務。
- 使用主動語態，寫清誰做什麼。
- 一句話只表達一個判斷；用句號斷開，不用分號串聯。
- 刪除填充詞：其實、基本上、非常簡單、只需要、值得注意的是。
- 刪除模糊量詞：一些、若干、適當、較快；改成具體數字或條件。
- 避免名詞堆疊：超過三個名詞修飾同一個詞時，拆成短句或加介詞。
- 時態保持簡單：一般現在時描述行為，一般過去時描述已發生的事。

## 第四步：改寫段落

- 一段只講一個主題。
- 每段最多 6 句；超過就拆分。
- 先給結論或目的，再給步驟或細節。
- 列表項保持平行結構，每項以同類詞開頭。
- 步驟編號連續，不跳號；每步只做一個動作。
- 警告和限制單獨成段，放在受影響步驟之前，不要放在文末。

## 第五步：自檢

交付前逐項檢查：

- 找出最長的三句，逐詞計數；超過上限就拆分。
- 搜尋縮寫、被動語態、進行時和分號，逐處確認是否必要。
- 檢查每個條件句：條件是否在指令之前。
- 檢查術語表：同一概念是否出現了兩個說法。
- 檢查程式碼塊、路徑、引數和錯誤原文是否被改動。
- 檢查是否有未經證實的絕對化表述，例如「總是」「絕不」「100%」。
- 檢查是否殘留營銷詞和空泛承諾。

## 常見替換

| 不要寫 | 改寫為 |
|---|---|
| 利用、使用某種能力 | 使用 |
| 為了 | 為了；或直接刪掉，改用目的句 |
| 在……之前 | ……之前 |
| 確保 | 確認；或寫出具體檢查動作 |
| 功能 | 功能；具體到某個操作時寫操作名 |
| 應該 | 必須（要求）或刪掉（建議） |
| 可能、也許、或許 | 能；或寫明觸發條件 |
| 進行最佳化 | 最佳化；直接寫優化了什麼 |

替換後必須通讀，確認沒有改變原意和承諾邊界。

## 輸出格式

改寫任務輸出：

1. **改寫後的文本**：完整可貼上版本。
2. **主要改動**：按類別列出，例如拆長句、統一術語、調整條件位置。
3. **未改動項**：程式碼、路徑、引數、引用原文。
4. **仍需作者確認**：涉及事實、數字或承諾邊界的地方。

檢查任務輸出：

- 逐條列出違規位置、問題型別和改寫建議。
- 按嚴重程度排序：可能導致誤操作的在前，風格問題在後。

## 邊界

- 不編造數字、版本、介面行為或相容性結論。
- 不把含糊的原意改得更絕對。
- 不為了短句刪掉必要的安全警告。
- 不改程式碼、識別符號、命令列引數、檔案路徑和引用原文。
- 不聲稱文本已通過簡化技術英語認證。
