# 追問式方案評審

## 何時使用

出現以下任一情況時使用本技能：

- 使用者要挑戰一個方案，驗證關鍵決策是否站得住。
- 計劃裡還有模糊目標、未驗證假設或互相沖突的約束。
- 實施前需要把「大概這樣」變成「每個分支都有明確選擇」。
- 使用者說「追問我」「評審這個方案」「幫我把計劃問清楚」。

不適用：已經有明確驗收標準的小改動；使用者只想直接要一份實現程式碼。

## 核心原則

1. **事實自己查，決策問使用者。** 程式碼裡能查到的不問；需要取捨的必須問。
2. **一次只問一個問題。** 連續拋多個問題會讓回答失焦。
3. **每個問題都帶推薦答案和理由。** 不讓使用者從零開始想。
4. **沿著決策樹走。** 先解決上游選擇，再問依賴它的下游問題。
5. **不確認就不進入實施。** 沒達成共識前，不寫規格、不拆任務、不改程式碼。

## 工作流程

### 1. 建立事實底稿

- 從對話、程式碼和已有文件中提取：目標、約束、現狀、已做過的嘗試。
- 工作臺檔案用 `read_file` 讀取，目錄用 `list_files` 列出；引用時標註路徑。
- 把內容分成兩類：
  - **事實**：能從程式碼、文件、介面或資料中驗證的內容。
  - **決策**：需要使用者權衡優先順序、成本、風險或偏好的內容。
- 事實不完整時先補事實，不把猜測包裝成問題。

### 2. 畫出決策依賴

- 列出必須解決的關鍵決策，標出先後依賴。
- 優先處理會推翻其他選擇的上游決策，例如範圍、目標使用者、相容性底線。
- 對每個決策寫出：可選方案、各自代價、推薦項、推薦理由。
- 刪除不影響結果的偽決策，避免把評審變成問卷。

### 3. 逐個追問

按依賴順序提問，每次只問一個：

- 先複述當前理解，確認沒有聽錯。
- 給出 2–4 個具體選項，說明代價和風險。
- 明確推薦哪一個，以及為什麼。
- 使用者回答後，記錄結論，指出它推翻了哪些先前假設。
- 如果回答引出新的事實缺口，先查證，再繼續。

追問要針對薄弱點，而不是重複確認：

- 這個方案在什麼條件下會失敗？
- 哪個假設一旦不成立，整個計劃就要重做？
- 出問題時如何回滾，誰來發現？
- 這個取捨是否為了省事而犧牲了不可逆的東西？
- 有沒有更小的版本能先驗證核心假設？

### 4. 處理分歧

- 使用者與推薦不一致時，先確認理解了對方的約束，再說明差異的代價。
- 無法當場決定時，標記為開放問題，寫明預設方案和觸發重新評估的條件。
- 不把「以後再說」當成已解決；開放問題必須有人負責、有時間點。

### 5. 確認門

在以下條件全部滿足前，不進入實施、寫規格或拆任務：

- 每個關鍵決策都有明確結論，或明確記為開放問題。
- 開放問題都有預設方案和負責人。
- 使用者明確表示理解並同意繼續，例如「確認」「可以」「按這個來」。
- 複述一遍最終方案，列出被放棄的選項及原因。

## 文件模式

當方案依賴具體庫、框架或外部 API 時，切換到文件模式：

- 列出方案依賴的每個外部行為和版本假設。
- 用 `web_fetch_page` 讀取官方文件或 API 參考，優先一手來源。
- 逐條核對：方法簽名、引數、版本差異、棄用狀態、錯誤語義。
- 標註「已確認」「已糾正」「仍不確定」三類結果。
- 對仍不確定的點，建議做最小驗證實驗，而不是繼續推理。

不確定時明確說不確定，不要用訓練記憶替代文件。

## 輸出格式

每輪追問後輸出：

- **當前共識**：已經確認的目標、約束和決策。
- **本輪問題**：一個問題，附選項、推薦項和理由。
- **受影響的假設**：這次回答改變了什麼。
- **待辦驗證**：需要查程式碼、查文件或做實驗的事項。

結束時輸出：

- **最終方案**：一段話概括。
- **關鍵決策表**：決策、選擇、理由、放棄的選項。
- **開放問題**：問題、預設方案、負責人、複查時間。
- **實施前置條件**：開始動手前還必須滿足什麼。

## 邊界

- 不替使用者做需要業務判斷的決定。
- 不用連續提問消耗使用者耐心；能自己查的一律自己查。
- 不把追問變成挑刺，每個問題都要指向一個真實的取捨。
- 不在確認門前偷偷開始寫實現。

## 來源與改編

改編自 bigpowers 的 `grill-me`（作者 Daniel，MIT 許可證，版本 2.88.9）。原技能包含 `WebFetch` 和參考檔案；本版改為純提示詞流程，用內建網頁讀取工具核對文件，保留事實與決策分離、單問題追問和確認門。
