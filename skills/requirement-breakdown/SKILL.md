# 需求拆解與驗收標準

## 何時使用

出現以下任一情況時使用本技能：

- 使用者給出一句話需求或會議結論，要求拆成開發任務。
- 需要在開發前補齊驗收標準、邊界場景和非功能要求。
- 需要判斷一個需求是否足夠清晰、能否進入排期。
- 需要把大需求拆成可獨立交付的切片。

不適用：替產品負責人決定優先順序、估算工時、或把未確認的假設寫成確定需求。

## 輸入

必需：

- 需求描述：要解決的問題或要交付的能力。
- 目標使用者：誰使用、在什麼場景使用。

可選：

- 業務目標或衡量指標。
- 現有流程、系統限制和技術約束。
- 截止時間、合規要求、依賴團隊。
- 已知的競品做法或使用者反饋。
- 不在本次範圍內的內容。

資訊不足時，先輸出「待確認問題」，不要用假設填滿整個方案。

## 拆解原則

1. **問題優先於方案**：先確認要解決的使用者問題，再討論功能。
2. **每個切片可獨立交付**：切片之間儘量少共享未完成依賴。
3. **驗收標準可觀察**：用 Given / When / Then 描述外部可見行為，不寫「程式碼實現正確」。
4. **邊界顯式化**：空狀態、失敗、許可權、併發、超限都要有定義。
5. **非功能要求單獨列**：效能、安全、可用性、相容性不混在功能描述裡。
6. **範圍外寫清楚**：明確本次不做什麼，防止範圍蔓延。
7. **開放問題有負責人**：每個未決問題寫清找誰確認、何時需要答案。

## 工作流程

1. **複述問題**：用一句話說明「誰在什麼場景下遇到什麼問題」，讓使用者確認。
2. **定義目標**：寫出一個可衡量的成功指標，區分結果指標和過程指標。
3. **識別角色**：列出主要使用者、次要使用者和受影響的內部角色。
4. **走主流程**：按使用者動作順序寫出正常路徑，標出系統響應。
5. **補邊界**：逐個檢查空、錯、慢、多、少、無許可權、重複提交。
6. **拆切片**：按使用者價值或依賴順序切成可獨立驗收的條目。
7. **寫驗收標準**：每條切片給出 2–5 條 Given / When / Then。
8. **列非功能與依賴**：補充效能、安全、相容、上線和資料要求。
9. **收斂問題**：把無法自行決定的點整理成開放問題清單。
10. **自檢**：確認沒有遺漏角色、狀態和失敗路徑。

## 輸出格式

```markdown
# 需求拆解：<需求名稱>

## 1. 問題與目標

- 使用者問題：<誰在什麼場景下遇到什麼問題。>
- 業務目標：<要改善的指標或結果。>
- 成功標準：<可衡量的數字或可觀察的狀態。>

## 2. 範圍

**本次包含**

- <能力一>
- <能力二>

**本次不包含**

- <明確排除項>

## 3. 使用者故事

| 編號 | 角色 | 我想要 | 以便 | 優先順序 |
|---|---|---|---|---|
| US1 | <角色> | <能力> | <價值> | P0/P1/P2 |

## 4. 主流程

1. <使用者動作> → <系統響應>。
2. <使用者動作> → <系統響應>。

## 5. 驗收標準

### US1：<故事標題>

- **AC1**：Given <前置條件>，When <動作>，Then <可觀察結果>。
- **AC2**：Given <異常條件>，When <動作>，Then <錯誤提示或降級行為>。

## 6. 邊界與異常

| 場景 | 預期行為 | 備註 |
|---|---|---|
| 空資料 | <展示空態/禁止提交> | |
| 無許可權 | <拒絕並提示> | |
| 重複提交 | <冪等或去重> | |
| 超時/失敗 | <重試或報錯> | |
| 超限 | <截斷/分頁/限制> | |

## 7. 非功能要求

- **效能**：<響應時間、併發量、資料規模。>
- **安全**：<鑑權、越權、輸入校驗、敏感資料。>
- **相容**：<舊資料、舊介面、客戶端版本。>
- **可用性**：<失敗降級、重試、告警。>
- **合規**：<留存、脫敏、審計。>

## 8. 依賴與風險

| 依賴/風險 | 影響 | 負責方 | 需要時間 |
|---|---|---|---|
| <依賴項> | <阻塞範圍> | <團隊/人> | <日期> |

## 9. 開放問題

| 問題 | 為什麼需要確認 | 找誰確認 | 截止時間 |
|---|---|---|---|

## 10. 建議交付順序

1. **切片一**：<內容>；依賴 <無/項>；驗收 <AC 編號>。
2. **切片二**：<內容>；依賴 <切片一>；驗收 <AC 編號>。
```

## 驗收標準寫法

- **可觀察**：寫使用者能看到的結果、介面返回或資料變化。
- **可判定**：不同人執行同一用例得到同一結論。
- **獨立**：一條標準只驗證一個行為。
- **帶條件**：前置狀態、操作和結果都寫清楚。
- **避免實現細節**：不寫「呼叫某函式」「新增某張表」，除非這是外部契約。
- **失敗也算驗收**：錯誤提示、拒絕、回滾都要有標準。

反例：「登入功能正常。」
正例：「Given 已註冊使用者，When 輸入正確賬號密碼並提交，Then 進入工作臺且會話保持 7 天。」

反例：「效能良好。」
正例：「在 1000 條記錄、單使用者條件下，列表首屏響應時間不超過 800 毫秒。」

## 切片規則

- 每個切片能獨立上線或獨立驗收；不能獨立上線時說明依賴。
- 優先切出使用者可感知的價值，而不是按技術層切。
- 共享基礎能力先做成最小可用版本，再疊加場景。
- 單個切片建議不超過 3 天；超過則繼續拆。
- 切片之間避免迴圈依賴；無法避免時明確先後順序。

## 邊界場景清單

- 空列表、首次使用、無歷史資料。
- 欄位缺失、格式錯誤、超長輸入。
- 未登入、無許可權、角色切換。
- 網路失敗、服務超時、部分成功。
- 重複點選、併發修改、順序錯亂。
- 資料量超過一頁、超過上限、匯出大檔案。
- 刪除後恢復、撤銷、回滾。
- 時區、語言、金額精度和單位差異。

## 質量檢查清單

- [ ] 使用者問題能用一句話說清。
- [ ] 成功標準可衡量。
- [ ] 每個使用者故事都有驗收標準。
- [ ] 驗收標準使用 Given / When / Then 且可觀察。
- [ ] 空、錯、慢、多、少、無許可權六類邊界已覆蓋。
- [ ] 非功能要求單獨列出。
- [ ] 範圍外內容明確。
- [ ] 開放問題都有負責人和截止時間。
- [ ] 切片可獨立交付或有明確依賴順序。

## 邊界

- 不替產品負責人決定優先順序和商業取捨。
- 不估算具體工時，只給相對順序和依賴。
- 不把技術方案當成需求本身。
- 涉及合規、隱私或支付時，提示需要對應負責人確認。
