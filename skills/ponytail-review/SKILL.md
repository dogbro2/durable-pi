# 精簡程式碼評審

## 何時使用

出現以下任一情況時使用本技能：

- 使用者要求評審未提交改動、某個分支、某次提交或 PR。
- 需要判斷改動是否過度設計，哪些程式碼可以直接刪掉。
- 需要按嚴重程度給出可執行的評審意見。
- 使用者說「review 一下」「看看這個改動」「有沒有更簡單的寫法」。

不適用：需要執行完整測試套件代替人工判斷；對沒有上下文的程式碼片段做風格挑刺。

## 核心立場

像剛接手程式碼、出故障會被叫去處理的資深開發那樣評審。重要性順序：

1. 正確。
2. 安全。
3. 在預期負載下扛得住。
4. 風險邏輯有測試。
5. 夠快。
6. 夠精簡。

精簡仍然重要：多出的每一行以後都要被人讀、被測試、被修復。

## 第一步：先理解

- 明確評審物件：未提交改動、暫存區、某個分支、PR 連結或指定檔案。使用者沒說時，預設看未提交改動；沒有改動就看最後一次提交。
- 先讀 diff，再讀它接觸的程式碼：被改函式的呼叫方、它呼叫的函式、相關測試、README。
- 工作臺檔案用 `read_file` 讀取，目錄用 `list_files` 列出；引用時標註路徑和行號。
- 追蹤真實資料流：輸入從哪裡來、存了什麼、輸出到哪裡。
- 改動可能破壞它沒碰到的程式碼。簽名、返回值或行為變化時，逐個檢查呼叫方。
- 從 README 和部署配置判斷預期負載：單人指令碼，還是多使用者、多程序併發。明確寫出你假設的負載。

## 第二步：按順序找問題

### 1. 缺陷

- 結果錯誤、崩潰、漏掉的邊界：空值、零、最後一項、舍入、時區。
- 呼叫方因改動而失效。
- 同一個規則在兩個地方實現不一致。
- 只在某個呼叫點修了，共享函式仍然有問題。

### 2. 風險

- 安全漏洞：注入、弱隨機數、硬編碼金鑰、缺少輸入校驗。
- 資料丟失：吞掉錯誤、寫入順序錯誤、沒有事務。
- 許可權邊界缺失或校驗放錯層。

### 3. 規模

- 單使用者沒問題、多使用者會壞：先查後寫的競態、每個程序重複做同一件事。
- 只增不減的記憶體或列表、逐項查詢、大輸入上的平方級複雜度。
- 本應共享的狀態放在程序內。

### 4. 缺失測試

- 有風險的新邏輯沒有能在壞掉時失敗的測試：分支、解析器、金額、安全、資料寫入、缺陷修復。
- 要一個好測試，不要覆蓋率數字。
- 測試只驗證實現細節，而不是公開行為。

### 5. 速度

- 明顯變慢是問題。
- 熱迴圈裡的重複計算是建議，不是阻塞項；有些軟體確實在乎每一毫秒。

### 6. 精簡

- **刪除**：死程式碼、沒人用的選項、沒人設定的配置、投機性功能。
- **複用**：倉庫裡已有同樣的 helper，指出路徑。
- **標準庫或平臺**：標準庫或平臺已經能做；為幾行程式碼新增依賴。
- **YAGNI**：只有一個實現的介面、只有一個產品的工廠、只轉發呼叫的包裝層。
- **合併**：必須一起改的近似重複程式碼。
- **拆分**：一個函式做幾件不相關的事，難讀難測。按職責拆，不按行數拆，不製造只為縮短函式的 helper。

## 第三步：報告前核實

- 每個問題都要有具體場景：「這個輸入或這個狀態會導致這個錯誤結果」。沒有場景就不算問題。
- 報告前重讀相關行，確認呼叫方真的存在、值真的可能為空、程式碼真的沒人用。
- 判斷程式碼未使用前，全倉搜尋，包括測試、fixture、配置、字串和動態引用。
- 標了 `shortcut:` 或 `ponytail:` 並寫明限制的捷徑是決策，不是問題；除非預期負載已經越過該限制。
- 提出能工作的最小修復，優先刪程式碼。
- 不新增問題不需要的層、框架或配置。
- 不寫風格偏好、不寫「可以考慮」、不寫模糊擔憂。

## 第四步：輸出

用簡單直白的語言，短句，日常詞。技術術語第一次出現時解釋。讀者可能從沒見過這段程式碼。

開頭用兩三句話寫「這個改動做了什麼」，並說明假設的負載。

按三組輸出，從最重要到最次要，跳過空組：

- **必須修**：缺陷、安全、資料丟失、在預期負載下會壞。
- **應該修**：有風險但沒測試的程式碼、真實變慢、重複、職責混雜、本不該存在的程式碼。
- **可以更好**：小的提速、更短的寫法。

所有問題統一編號，方便使用者說「修 2 和 5」。最多 20 條；省略了較小問題就說明省略了幾條。

每條問題包含四部分，每部分一到兩句：

1. **是什麼**：這段程式碼在做什麼。
2. **問題**：哪個輸入或狀態會導致什麼錯誤結果。
3. **修復**：最小可行改動，優先刪程式碼。
4. **不修的後果**：誰會受影響，影響是什麼。

結尾寫：

- **結論**：可以合入，或先修哪幾條。
- **精簡空間**：可以刪掉多少行、去掉多少依賴（如果有）。
- **未檢查項**：沒讀到的部分或無法執行的驗證，一行說明。

沒發現問題時，寫「這個改動做了什麼」，然後「看起來沒問題，可以合入」，再用一行說明檢查了什麼。

## 邊界

- 只評審，不改程式碼。
- 不把個人風格偏好寫成阻塞項。
- 不因為沒有測試就要求補全整個測試套件；只要求覆蓋高風險邏輯。
- 不把安全建議降級為「可以考慮」。

## 來源與改編

改編自 Dietrich Gebert 的 `ponytail-review`（MIT 許可證，ponytail 5.3.2）。原技能通過外掛和本地 hook 使用；本版改為純提示詞版本，保留評審順序、具體場景要求和四段式問題格式，去掉本地命令依賴。
